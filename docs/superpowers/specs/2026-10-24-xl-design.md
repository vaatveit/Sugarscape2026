# Sugarscape xl — Design

Date: 2026-10-24. Builds on [the project design](2026-10-21-sugarscape-design.md) and
[the viewer design](2026-10-24-viewer-design.md).

## Intent

The point of scaling Sugarscape up is to **compare the performance of different implementations**: this Python
model, the FLAME GPU 2 port in `flamegpu/`, and a Julia implementation not yet started. They need one shared,
larger workload. "xl" is that workload: the same sugarscape at 10× the linear resolution, 500×500 instead of 50×50,
with every distribution of resources and agents scaled so that an xl run **looks like a regular run, only more
detailed**.

xl is defined by **data and a written spec**, not by Python code that other implementations would have to copy.

**Goals**
- A committed 500×500 capacity map, `sugarscape/maps/sugar-map-xl.txt`, made from `sugar-map.txt` by a committed
  generator (the blur code). Other implementations load the file; they never run the generator.
- A language-neutral spec, `docs/xl.md`, saying exactly how a regular configuration becomes its xl configuration,
  for the FLAME GPU and Julia work to implement later.
- In Python: an xl switch in the experiment runner and in the viewer, both built on one config transform.
- Timing of the Python baseline: the runner records setup, stepping and metrics time for every seed it runs, and
  the spec defines the same measures for the other implementations.

**Non-goals**
- FLAME GPU or Julia support for xl (user decision: stop at the spec and the map file). The GPU bridge's existing
  check refuses xl configs, because they change fields it does not read (`sugar_map`, and `diffusion_passes` when
  diffusion is on). That refusal is correct and stays.
- Making the Python model faster. It is the baseline being measured; its xl speed (about 4–6 s per period for
  II-4's rules, 6–10 s early in VI-1, measured on a prototype) is a result, not a defect.
- Scoring xl runs against the book's targets. The targets are absolute numbers for a 50×50 world.
- xl for Schelling and Ring World. They are separate worlds with their own sizes.
- Zoom and pan in the viewer (user decision: the whole world at once).
- Changing the GPU benchmark's tiling (K×K copies of the 50×50 map). It is a different workload and stays.

**Anti-goals**
- **The xl map must not move the original terraces.** Upscaling may only refine edges (the round-trip properties
  below are tested).
- **No regular run changes.** Every existing experiment keeps its config, its random stream, its results, and its
  fingerprint in `experiments/run.py`, so saved `results/` stay current.
- **The viewer must faithfully represent the data** (the user's standing anti-goal from the viewer design). At xl,
  this includes never showing an agent in a color that can't be told apart from the cell beneath it.

## The xl map (user decision: smooth contours, 0.5-cell blur)

The 50×50 map has five terraces (capacity 0–4). The top terrace is exactly two discs of radius 5.75 about
(14.5, 14.5) and (38.5, 38.5). The lower ones are close to discs but hand-shaped (30–108 cells differ from any disc
fit, the saddle between the peaks is filled, and the map is only 58% symmetric under a half turn). So the map is not
replaced by a formula. Each terrace boundary is redrawn at 10× resolution instead.

**Algorithm** (all float64; coordinates in coarse-cell units, coarse cell i has centre i + 0.5; no wrapping, since
the 50×50 map's edges do not match across the torus):
1. For each level ℓ = 1, 2, 3, 4, let the region be the coarse cells with capacity ≥ ℓ.
2. **Signed distance at coarse centres:** for each coarse cell, the Euclidean distance between centres to the
   nearest cell on the other side of the region boundary: positive inside the region, negative outside.
3. **Bilinear interpolation** of that field to the 500×500 fine-cell centres. Fine cell j has centre (j + 0.5)/10 in
   coarse units, so it sits at coarse index (j + 0.5)/10 − 0.5. Positions beyond the outermost coarse centres take the
   edge value (clamped).
4. **Gaussian blur** with σ = 5 fine cells (0.5 coarse cells): separable, kernel truncated at 3σ (radius 15),
   normalised to sum 1, with edge-replicating padding.
5. A fine cell is inside level ℓ if its blurred value is > 0 **and** it is inside level ℓ − 1 (so terraces nest).
6. Fine capacity = the number of levels the cell is inside (0–4, whole numbers).

**Measured properties of the result** (prototype; the generator's tests pin them):
- In every 10×10 block, the centre cell (offset 5, 5) and the majority value both equal the original coarse value:
  all 2,500 blocks.
- Each capacity's area is 100× its original area to within 1.1%: ratios 0.9985, 0.9992, 1.0028, 1.0024 and 0.9893
  for capacities 0 to 4. Total capacity is 0.9996× of 100× the original.
- The closest any blurred value comes to the threshold is 3.4 × 10⁻⁴, far above float64 rounding error, so the
  file regenerates identically on any machine.
- More blur rounds the discs further but moves terraces: at σ = 0.8 coarse cells, 6 block centres change and the top
  terrace loses 2.3%. 0.5 is the most blur that keeps every block.

**File:** the same format and orientation as `sugar-map.txt`: whitespace-separated integers, one line per row, the
first line northernmost (`load_map` reads it). About 500 KB. **Spice:** as now, the spice map is the sugar map
mirrored east–west. Upscaling and mirroring commute, so no second file is needed.

**Generator:** in the repository (location is the builder's), numpy only, runnable as a module to rewrite the file.
Its test regenerates the map and requires equality with the committed file, plus the properties above.

## The xl configuration (the spec's core)

xl applies to a regular sugarscape `Config` on the 50×50 map. Everything measured in cells scales by 10 along each
side; everything counted per area scales by 100; everything per agent or per period is unchanged.

| Setting | Regular | xl | Basis |
|---|---|---|---|
| World | 50×50 | 500×500 | user request |
| Map | `sugar-map.txt` | `sugar-map-xl.txt` | above |
| Founders `initial_population` | N | 100·N | same crowding (user request) |
| Vision range `vision` (lo, hi) | e.g. (1, 6) | (10·lo, 10·hi), **every whole number in it** | user decision: agents see the same share of the world; the draw is uniform over all integers in the range |
| Start block `block` (x0, y0, w, h) | e.g. (0, 0, 20, 20) | (10·x0, 10·y0, 10·w, 10·h) | user request |
| Tribal blocks `initial_blocks` (tribe, x0, y0, w, h, n) | e.g. (blue, 0, 0, 20, 20, 270) | (tribe, 10·x0, 10·y0, 10·w, 10·h, 100·n) | user request |
| Diffusion passes per diffusion period | 1 | 100 | *my call:* one pass spreads pollution about 0.7 cells (standard deviation); n passes spread √n times as far, so 100 passes cover the same share of the world |
| Everything else (metabolism, endowments, ages, fertility, foresight, growback, seasons, pollution rates, trade, credit, culture, combat, disease, seeds, steps) | | unchanged | per agent, per cell or per period |

Notes:
- Seasons already split the world at `height // 2`, so they scale with it.
- Everything that looks as far as vision reaches 10× as far automatically, as movement does: mate search within
  vision (the default rule S contact), and combat (rule C replaces movement; it picks targets and checks for
  retaliation along the lattice out to vision). This follows from the user's decision that vision scales.
- Trade, culture and disease still act between the four adjacent agents (*my call*): crowding is the same and agents
  travel as far in world terms, so each meets about as many others per period.
- The largest vision in the registry, (5, 24) from IV-13/v14.5 → (50, 240), is still less than half of 500, so
  `Config`'s vision check passes for every registered experiment.
- An xl run is a different random stream from its regular run. Implementations are compared by statistics and by
  timing, never cell by cell.

**New `Config` field:** `diffusion_passes: int = 1`, meaning the passes of the D rule per diffusion period. It is
declared like the rule S options, `field(default=1, repr=False)`, so no existing fingerprint changes. The
`experiments.run.fingerprint` mechanism already adds such fields when they leave their default. It must be ≥ 1.

**The transform:** one Python function maps a regular `Config` to its xl `Config` following the table. It refuses
any config that isn't 50×50 on `sugar-map.txt`, so xl can't be applied twice.

## The spec document, `docs/xl.md`

Written for someone implementing xl in another language, without reading the Python. It contains:
- what xl is for, and that it's defined by the table and the map file;
- the map file's format, orientation and checksum (SHA-256 of the committed file), and the spice mirroring;
- the configuration table, with the diffusion reasoning;
- the generator's algorithm, as above, for anyone who wants to rebuild or audit the map;
- what "implements xl" means: it loads `sugar-map-xl.txt` and applies the table; results agree statistically, not
  cell by cell;
- the three timing measures (setup, stepping, metrics), as the runner defines them, so every implementation
  reports the same things; how results must agree is left to the comparison work;
- the Python reference: the transform, `--xl`, and the viewer switch.

## Python surfaces

### Runner (`experiments/run.py`)
- `--xl` runs the xl version of each matching experiment, with the same seeds and steps.
- xl results go to their own folder (*my call:* `results-xl/` by default, so `--out` still overrides) and never mix
  with the regular `results/`. Their fingerprint is the xl config's, so a change to the transform or the map makes
  them stale.
- Schelling and Ring World ids with `--xl` are an error naming the reason.

### Timing (user decision: record the Python baseline now)
- For every seed it runs, xl or regular, the runner records wall-clock time (`time.perf_counter`) in three parts:
  - **setup:** building the model, including loading the maps and placing the founders;
  - **stepping:** the total over all periods of the model's own step;
  - **metrics:** the total time spent collecting each period's metrics, which the runner does, not the model.
- It also records the number of periods and the agent count at the start and at the end.
- These go to a `timing.csv` in the experiment's result folder, one row per seed. The folder also gets a note of
  the machine and the conditions: Python and numpy versions, platform, processor, and `--jobs`. Timings taken with
  `--jobs` above 1 share the processor, and the note says so.
- `timing.csv` is separate from the per-seed result CSVs and from the fingerprint, so it changes neither the result
  files' layout nor whether saved results count as current.
- `docs/xl.md` defines the same three measures, so FLAME GPU and Julia can report comparable numbers. *Not decided
  here:* how implementations' results must agree (which metrics, how many seeds, what tolerance). That belongs to the
  comparison work, and the spec says so.

### Viewer (user decision: the whole world at once)
- An **xl** switch beside Start. The run information says when a run is xl.
- The board draws the whole 500×500 world. Each cell is one solid color, with no smoothing between cells, so no
  color appears that isn't a cell's or an agent's own.
- **Board size at xl (*my call*, after the builder check):** every cell gets the same whole number of device
  pixels, k × k. The board is the largest whole multiple of 500 device pixels that fits the space the layout gives
  it, and never less than 500 (k = 1). Where even 500 doesn't fit, the board keeps 500 device pixels and the page
  scrolls. That way no row or column is dropped, which would hide agents, and none is drawn wider than the rest.
  At the common devicePixelRatio of 1.5, k = 1 is 333 CSS pixels and k = 2 is 667.
- **Agents at xl fill their cell** in their attribute color. **Size encoding is off** at xl, because every dot would
  be smaller than a pixel. The size menu is disabled, and the legend says why.
- **Kept periods:** an xl frame is about 2.5 MB, against about 25 KB regular, so an xl run keeps the newest 100
  periods instead of 500 (*my call*, about 250 MB). The chart caption and the slider's minimum already report the
  window, so they show 100.
- Hover still reports the exact cell under the pointer. At about one pixel per cell, landing on a particular agent
  is hard, and that is accepted.
- **Agent and cell colors at xl (user decision: muted landscape underneath).** On today's palettes, an agent filling
  its cell can be indistinguishable from the cell. The palest wealth bands match some cell colors exactly
  (contrast 1.00), and the tribe colors reach only 1.4–1.7 against the worst cell. At regular size the dark outline
  solves this; at one pixel there is no room for one. So xl uses its own palettes, as fixed functions like every
  other encoding:
  - **Cells:** the same blend, white + w·s/smax·(yellow − white) + w·p/pmax·(rust − white), with a smaller weight
    w for xl (the builder picks it), so the landscape is paler. All 33 × 33 (sugar, spice) pairs in eighths must still
    draw as distinct colors (tested, as for the regular weight).
  - **Agents:** xl colors for the two tribes, the neutral color, and the five wealth bands. Each must have a contrast
    of at least 3:1 against every xl cell color (tested, as the outline is now). The wealth bands keep their order,
    lighter to darker with wealth, and must stay distinguishable from one another by a tested criterion the plan
    states. The tribe colors stay red and blue in hue, as the book colors the tribes.
  - Regular runs keep today's palettes unchanged. The legend shows whichever palettes the current run uses.

## Verification

- **Map:** the generator reproduces the committed file exactly, and the block-centre, block-majority and area
  properties hold. `load_map("sugar-map-xl.txt")` has shape (500, 500), values 0–4.
- **Transform:** every row of the table, on configs with and without blocks and tribal blocks. It refuses non-50×50
  input. It applies to every registered `Config` experiment without error, and the resulting `Model` builds for a
  representative few (II-4, II-6, III-11, IV-A3).
- **No regular change:** every registered experiment's `fingerprint` is unchanged by this work. A test compares
  them against values recorded before the change.
- **Diffusion passes:** `diffusion_passes = n` gives the same pollution as n single diffusions.
- **Runner:** `--xl` writes to the xl folder with the xl fingerprint, and refuses Schelling and Ring World.
- **Timing:** `timing.csv` has one row per seed, with non-negative setup, stepping and metrics times and the right
  period and agent counts. The machine note exists. The seed CSVs and fingerprints are byte-for-byte what they were
  before timing was added.
- **Viewer:** the server starts an xl run and reports it; frames are 500×500; xl keeps 100 periods. The xl
  palettes pass their distinctness and 3:1 contrast tests. The board-size rule gives every cell k × k device pixels,
  with k ≥ 1.
