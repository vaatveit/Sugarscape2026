Generated by `python -m bridge.xl_validate` (xl design, section 5). Each metric is compared at 10%, 25%, 50% and 100% of the run's periods, as the GPU's seed mean against Python's.

- **Gap:** |GPU − Python| as a percentage of the metric's scale, the largest |Python mean| over the run.
- **Spread:** Welch's t over seeds.
- A comparison **disagrees** when its gap is over 1% *and* |t| > 3 (or there is no spread on both sides, so no t).
- A metric undefined (nan) in every seed on one side only is **undefined on one side**, listed with the disagreements. One undefined on both sides, or whose Python scale is 0, is not judged. Seeds where a metric is undefined are left out of its means; the n columns count the seeds that remain.

- **What fixed them.** A Python harness kept Python's model and swapped parts of a period (5 xl seeds per variant):
  - **II-6 came from how contested sites were resolved.** On the GPU every agent picked from the round's start
    state, and a loser picked again after agents later in the order had taken the sites it would have reached first
    in Python's order.
    - Python with the GPU's old rounds reproduced the GPU's deficit: north-east fraction −18%, `moved` within 0.1%
      of the GPU's.
    - Python with deferred acceptance reproduced Python exactly.
    - The GPU now resolves moves that way. Tests replay periods from the dumps and match every agent's site.
  - **II-8 came from when neighbours were counted.** The GPU counted after everyone had moved; Python counts each
    agent right after its own move and metabolism.
    - Python's own moves with the GPU's old counting reproduced both the spikes (+31% at t = 1, +46% at t = 102)
      and the steady −4 to −6% after diffusion.
    - The previous report called the steady part "a separate effect" because its sign is opposite to the spikes'.
      That was wrong: both came from the counting.
    - The GPU now counts in the period's order.
- **II-6 now.**

    (t = −0.24). Before, it was −10 to −15%, lasting.
